# SVG Refinement Demo — Coding Agent Plan

## 1. Goal

Build a **minimal working demo** for post-processing SVG road-sign graphics generated by a locally fine-tuned small VLM.

The local VLM already produces SVGs that are visually close to the reference PNG. Most required elements already exist and are approximately correct.

This project is **not** another image-to-SVG generator.

The goal is to:

> Preserve the existing SVG as much as possible and repair only local semantic, geometric, alignment, text, arrow, and layering errors.

The workflow should use:

- a multimodal foundation model through **AWS Bedrock**
- structured analysis of the existing SVG
- deterministic SVG manipulation functions
- iterative render → inspect → repair → render cycles

The priority is **getting a useful demo running**, not building a production system.

---

# 2. Very Important Implementation Constraints

These constraints are mandatory.

## 2.1 Keep the implementation small

Do not build unnecessary infrastructure.

Do **not** add:

- multi-agent frameworks
- LangChain / LangGraph unless absolutely required
- databases
- queues
- asynchronous job systems
- distributed processing
- plugin systems
- generic workflow engines
- complex configuration systems
- web UI
- production deployment code
- extensive logging infrastructure
- telemetry
- authentication
- caching layers
- elaborate exception hierarchies
- generalized geometry frameworks

A simple Python workflow is preferred.

---

## 2.2 Do not over-engineer testing

This is a prototype.

Do not spend significant implementation time or tokens on:

- exhaustive unit tests
- large test matrices
- fuzz testing
- synthetic edge-case generation
- performance benchmarks
- integration-test infrastructure

A few simple sanity checks are enough if they are necessary to run the demo.

The priority is:

1. implement the workflow
2. run it on real example SVGs
3. inspect the output
4. adjust the logic

---

## 2.3 Do not solve hypothetical problems

Implement only requirements described in this document.

Do not add support for hypothetical SVG formats, arrow types, fonts, providers, or workflows unless they are required by actual example data.

When uncertain, choose the simplest implementation that works with the current data.

---

## 2.4 Do not rewrite the SVG unnecessarily

The local VLM output is already valuable.

The refinement system must preserve existing elements wherever possible.

Except for **arrow path repair**, existing path geometry must not be regenerated.

# 3. Inputs

Each refinement task receives:

1. `reference.png`
   - target road-sign image
   - used as visual ground truth

2. `input.svg`
   - SVG generated by the local fine-tuned VLM

3. current rendered SVG image
   - generated locally from `input.svg`
   - same canvas size as the reference image in normal cases

The reference PNG and SVG normally use:

- the same canvas size
- the same orientation
- no intentional padding
- approximately corresponding image coordinates

Only reasonably good VLM outputs will be sent into this refinement workflow.

The workflow does not need to rescue completely broken SVG generation.

---

# 4. High-Level Architecture

Use a **single orchestrated refinement workflow**.

Do not implement multiple autonomous agents.

Conceptually:

```text
Reference PNG
Input SVG
    │
    ▼
SVG Parsing / Normalization
    │
    ▼
Structured SVG Manifest
    │
    ├───────────────┐
    │               │
    ▼               ▼
Rendered PNG    Multimodal LLM
                    │
                    ▼
             Structured Repair Plan
                    │
                    ▼
          Deterministic SVG Tools
                    │
                    ▼
               Updated SVG
                    │
                    ▼
                  Render
                    │
                    ▼
             LLM Re-evaluation
                    │
          issues remain?
             │             │
            yes            no
             │             │
             └──── loop ───┘
```

The multimodal LLM should perform semantic and visual reasoning.

Python should perform actual geometric calculations and SVG modifications.

# 5. Responsibility Boundary

## 5.1 The multimodal LLM is responsible for

- understanding the reference image
- understanding the rendered SVG
- identifying semantic objects
- grouping SVG elements into semantic objects
- identifying which existing elements are already correct
- selecting reliable anchor elements
- detecting visible problems
- determining which elements are involved in a problem
- identifying semantic landmarks in arrow paths
- deciding which repair operation should be applied
- deciding which element should be used as the reference or anchor
- determining text content when OCR from the local VLM is incorrect
- evaluating the result after each repair iteration

The LLM should describe **intent**, not final numeric geometry.

---

## 5.2 Python / deterministic SVG tools are responsible for

- SVG parsing
- assigning stable element IDs
- path normalization
- extracting path nodes and segments
- coordinate transforms
- bounding-box calculation
- center calculation
- geometric distance calculation
- centerline calculation
- translation
- text scaling
- text positioning
- element reordering / z-order correction
- arrow point modification
- reflection / mirroring
- SVG serialization
- SVG rendering
- canvas-boundary checks

---

# 6. Critical Principle: No Raw Geometry Guessing by the LLM

The LLM should not invent final SVG coordinates such as:

```text
x = 382.74
y = 217.61
scale_x = 0.783
```

whenever those values can be calculated deterministically.

The LLM should instead return instructions such as:

```text
align these three shield layers to the outer shield center
```

or:

```text
fit this English text horizontally inside this region
```

or:

```text
the arrow apex should align with the shaft centerline
```

Python then calculates the required values.

---

# 7. SVG Preprocessing and Normalization

Before asking the LLM to reason about the SVG, convert the SVG into a normalized internal representation.

## 7.1 Stable element IDs

Assign a stable ID to each relevant element if it does not already have one.

Example:

```text
path_001
path_002
text_001
rect_001
group_001
```

These IDs must remain stable throughout one refinement task.

The LLM must refer to elements using these IDs.

---

## 7.2 Basic manifest information

For each relevant SVG element, expose information such as:

```text
id
element type
parent/group
z-order
fill
stroke
transform
bounding box
center
```

For text:

```text
text content
font family
font size
transform
bounding box
```

For paths:

```text
normalized path commands
absolute coordinates
path segments
candidate nodes / endpoints
bounding box
center
```

Do not expose unnecessary XML noise to the LLM.

---

# 8. Path Normalization

Path normalization is especially important for arrows.

The local VLM does not always begin drawing an arrow path from the same semantic location.

The path may:

- start from different parts of the arrow
- contain additional points
- contain slightly different command ordering
- contain curve control points mixed with geometric landmarks

Therefore:

> Never assume that a fixed path command index corresponds to a fixed semantic arrow point.

Normalize paths before semantic reasoning.

At minimum:

- convert relative commands to absolute coordinates
- preserve the original segment order
- expose segment type
- distinguish segment endpoints from curve control points
- make path nodes addressable using stable local identifiers

For example:

```text
path_017.node_00
path_017.node_01
path_017.node_02
...
```

The LLM may identify which nodes correspond to semantic landmarks.

---

# 9. Error Classes to Support

The first demo should focus on the following classes only.

## 9.1 Text content errors

Examples:

- incorrect Japanese character
- incorrect English word
- OCR mistake

Repair:

- replace text content
- preserve the surrounding layout initially
- perform text-layout correction later

---

## 9.2 Text width and position errors

Typical case:

Japanese text appears on one line and English text appears below it.

The English text may be:

- too wide
- strongly shifted to one side
- outside the intended area
- outside the SVG canvas
- overlapping another object

Exact pixel-perfect matching is **not required**.

The goal is:

- approximately match the reference position
- remain inside the intended region
- avoid obvious overlap
- remain inside the canvas
- visually resemble the reference layout

There are normally only two font families:

- one Japanese font
- one Latin/English font

The LLM does not need access to font files.

Text measurement and transform calculation should be performed locally.

If the actual fonts are available locally, use them through the renderer or text measurement mechanism.

Do not build a font-analysis subsystem.

---

# 10. Non-Arrow Path Modification Rule

For all non-arrow path objects:

> Path geometry must remain unchanged.

This includes:

- route shields
- national road shields
- prefectural road shields
- sign borders
- IC / highway panels
- colored background shapes
- decorative layered shapes

Allowed operations:

- translation
- element reordering
- grouping if needed internally
- moving the whole existing path

Do not:

- modify individual path nodes
- reshape the path
- regenerate the path
- simplify the path
- reconstruct the path

---

# 11. Composite Shape Alignment

Many road-sign symbols are constructed using several overlapping paths.

Examples:

- route shield
- national-road shield
- prefectural-road shield
- nested border
- colored IC / highway panels

The individual path shapes are often correct, but their positions are slightly offset.

Example:

```text
outer layer center  = (x1, y1)
middle layer center = (x2, y2)
inner layer center  = (x3, y3)
```

The LLM should:

1. identify that these paths belong to the same semantic object
2. determine which layer is already positioned correctly
3. select that layer as the anchor

Usually the largest or outer layer will be a good anchor, but do not hard-code this assumption if visual evidence says otherwise.

The deterministic tool should then translate the other paths so that the intended centers coincide.

Path geometry and size must not change.

---

# 12. Outer Border Alignment

Some sign borders are produced by multiple paths of different colors and sizes.

Common failure:

- top border looks thinner than bottom border
- left border looks thinner than right border

This is usually caused by slightly different centers.

Repair by:

1. identifying the border layers
2. selecting the most reliable layer as anchor
3. translating other layers so their centers align

Do not reshape the border paths.

---

# 13. Z-Order / Layer Repair

Some objects are visually correct but appear in the wrong SVG order.

Example:

```text
white text
green IC panel
```

If the green panel is written later in the SVG, it may cover the white text.

The LLM should identify:

- which elements belong to the same visual object
- which elements should be in front
- which elements should be behind

The deterministic tool should only reorder the SVG elements.

Typical intended ordering:

```text
background
↓
border / panel
↓
inner colored region
↓
symbol / text
```

Do not change geometry when a z-order correction alone solves the problem.

---

# 14. Arrow Handling

Arrow processing is the main exception to the "do not modify path geometry" rule.

Arrow paths may be modified locally.

The current local VLM usually handles simple arrow structures better than arbitrary diagonal arrows.

The important expected arrow types are approximately:

- straight upward arrow
- upward then left-turn arrow
- upward then right-turn arrow
- multi-arrow structures where multiple arrows initially overlap on a common vertical portion

There may occasionally be:

- single left arrow
- single right arrow
- single diagonal arrow

Do not build a large arrow-template library for the first demo.

Focus on arrow structures that actually appear in current example data.

---

# 15. Arrow Problem Type A: Internal Geometry

The local VLM usually learns local arrow drawing patterns correctly:

- arrow tip curves
- shoulder / wing curves
- shaft body
- individual Bézier-style segments

However, it may fail to preserve the global geometric relationship between them.

A common failure is:

- shaft width is approximately correct
- arrow-head curves are approximately correct
- shaft centerline and arrow-head center do not align
- one side of the arrow does not reconnect correctly
- the generated path finally connects two distant points using an incorrect straight segment
- visually the arrow appears to have a missing corner or malformed side

This is considered an **internal arrow geometry error**.

---

# 16. Arrow Semantic Landmarks

After path normalization, allow the multimodal LLM to associate path nodes with semantic arrow landmarks.

Possible landmarks include:

```text
shaft left boundary
shaft right boundary
shaft centerline

arrow apex

left head / shoulder landmarks
right head / shoulder landmarks

shaft-to-head junction on the left
shaft-to-head junction on the right

bottom-left shaft corner
bottom-right shaft corner
```

The exact landmark set may differ between arrow types.

Do not assume a fixed node number.

The LLM identifies semantic meaning.

Python performs numeric calculations afterward.

---

# 17. Straight Upward Arrow Repair

For a straight upward arrow:

1. identify the two shaft boundaries
2. calculate the shaft centerline
3. identify the arrow apex / head geometry
4. determine whether the arrow head is centered on the shaft centerline
5. identify which side is malformed

Preserve:

- shaft width
- approximate total arrow size
- approximate arrow location
- good existing curves whenever possible

Repair only the malformed head/junction region.

If one side is visually and geometrically correct while the opposite side is malformed:

> Mirroring the correct side around the shaft centerline is an allowed repair strategy.

Do not automatically mirror both sides.

---

# 18. Turn Arrow Repair

For an arrow that travels upward and then turns left or right:

The vertical shaft and horizontal shaft may have different widths.

Therefore:

> Do not assume one global shaft width for the whole path.

The relevant arrow-head alignment must be based on the centerline of the shaft directly connected to that arrow head.

Example:

```text
vertical section
      │
      │
      └────────►
                right arrow head
```

For the right arrow head:

- identify the upper/lower boundaries of the horizontal shaft
- calculate the horizontal shaft centerline
- align the arrow head relative to that centerline

The vertical shaft centerline is not the correct reference for the right-facing head.

The same principle applies to left-facing heads.

---

# 19. Arrow Problem Type B: Multi-Arrow Shared Base Alignment

Multiple arrow paths may represent different branches of the same road-sign arrow tree.

Their lower vertical portions should visually overlap.

The local VLM may generate all branches correctly but shift their starting regions slightly.

The result is an unnatural split or thickened base.

The system should:

1. identify paths belonging to the same arrow group
2. identify the common base / shared stem region
3. determine which path is best aligned with the reference image
4. use that path as the anchor
5. translate the other arrow paths so the intended base regions overlap

Do not scale the arrow paths merely to achieve base overlap unless visual analysis clearly indicates that scale itself is wrong.

---

# 20. Arrow Repair Order

Default order:

```text
normalize path
↓
identify arrow and semantic landmarks
↓
repair internal arrow geometry
↓
render
↓
align arrows within the same arrow group
↓
render
↓
validate arrow group
```

This is the default order because malformed internal geometry can make group alignment landmarks unreliable.

However, the orchestrator may skip an internal repair if the arrow itself is already correct.

---

# 21. Anchor-Based Refinement

The LLM should explicitly identify reliable elements before making repairs.

A reliable element is an object whose:

- size is approximately correct
- position is approximately correct
- appearance is close to the reference
- geometry should not be changed

Examples:

```text
correct outer shield path
correct sign border
correct arrow shaft
correct panel
correct text block
```

Whenever possible, repairs should be defined relative to these anchors.

Examples:

```text
align inner shield layers to path_021
```

```text
align arrow apex to the shaft centerline
```

```text
move text_012 inside panel_004
```

This is preferred over estimating absolute target coordinates from scratch.

---

# 22. Structured LLM Output

Do not ask the model to return free-form SVG code.

Use structured JSON-like results.

Exact schema may remain simple for the demo.

Each detected issue should contain information conceptually equivalent to:

```text
issue type
target element IDs
semantic object type
anchor element ID if applicable
recommended operation
confidence
short reason
```

Example operations may include:

```text

ALIGN_BORDER_CENTER

REORDER_ELEMENTS

REPAIR_ARROW_INTERNAL

```

For arrow repair, the LLM may additionally return semantic landmark mappings between normalized path nodes and arrow concepts.

# 24. Text Transform Strategy

The local VLM may generate text transforms where horizontal scaling is repeatedly incorrect.

Do not try to teach the LLM to directly calculate the SVG transform matrix.

Instead:

1. identify the intended text region
2. measure current rendered width
3. determine whether the text is clearly too wide
4. determine an approximate target width from:
   - reference layout
   - nearby text
   - parent panel
   - canvas boundary
5. calculate horizontal scaling locally
6. apply the required transform

Precision does not need to be perfect.

Prefer a visually safe result over pixel-perfect matching.

---

# 25. Canvas Boundary Handling

In normal cases:

```text
reference canvas size == SVG canvas size
```

Sometimes VLM generation may create:

- text outside the canvas
- unexpectedly large objects
- SVG content extending far beyond the intended canvas

Because only mostly-correct SVGs enter this pipeline, implement only basic handling.

For example:

- detect obviously out-of-canvas text
- bring text back inside the intended canvas
- report obviously abnormal large geometry rather than trying to reconstruct the entire image

Do not build a general malformed-SVG recovery system.

---

# 26. Iterative Refinement

The workflow should not assume that one repair pass solves everything.

After meaningful repair stages:

1. save updated SVG
2. render SVG
3. send updated render plus reference image and current manifest to the multimodal LLM
4. ask which significant issues remain
5. perform the next repair

A previous repair may reveal a new problem.

Example:

```text
before:
arrow bases are misaligned

repair:
align arrow bases

after:
text now visibly overlaps the corrected arrow
```

The workflow should allow this new text issue to be repaired in the next iteration.

---

# 27. Avoid Endless Refinement

For the demo, use a small hard iteration limit.

Do not build convergence algorithms.

A simple limit such as a few refinement passes is sufficient.

The workflow should stop when either:

- the LLM reports no important remaining issue, or
- the iteration limit is reached

Minor visual differences can remain.

---

# 28. Suggested Default Repair Priority

Use approximately this priority:

```text
1. Parse / normalize SVG

2. Identify semantic objects and reliable anchors

3. Correct clearly wrong text content

4. Fix z-order problems

5. Align layered shield / border / panel elements

6. Repair internal arrow geometry

7. Align multi-arrow shared bases

8. Correct text width and position

9. Repair obvious collisions or out-of-canvas text

10. Final visual validation
```

This is a default priority, not a rigid state machine.

If a stage is unnecessary, skip it.

---

# 29. Bedrock Usage

Use AWS Bedrock for multimodal reasoning.

The first demo does not require a provider abstraction layer.

Implement the Bedrock call simply.

The selected model should receive enough context to compare:

- reference PNG
- current rendered SVG PNG
- structured SVG manifest
- current repair history if useful

Use the strongest available multimodal model appropriate for the experiment.

Do not design a general multi-provider abstraction unless it becomes necessary later.

---

# 30. Prompting Strategy

Prefer several focused reasoning steps over one huge instruction asking the LLM to completely repair the SVG.

For example:

### Initial analysis

Ask the LLM to identify:

- semantic objects
- correct anchors
- major visible differences
- element grouping

### Repair-specific analysis

For a selected issue, ask:

- which SVG elements belong to this object
- which element is the anchor
- which operation should be used
- for arrows, which normalized path nodes correspond to required semantic landmarks

### Validation

After a repair, ask:

- was the target issue fixed
- did a new obvious issue appear
- what significant issue should be repaired next

Do not let the LLM directly rewrite the complete SVG.

# 34. Demo Success Criteria

The first demo is successful if it can take one real VLM-generated SVG and visibly improve several of the following problems:

- misaligned layered route shield
- uneven nested border
- incorrect text
- overly wide English text
- text outside canvas
- incorrect z-order

It is **not required** to solve every possible road sign.

# 38. Main Architectural Principle

The project should follow this rule throughout:

> **Use the foundation model to understand what is wrong.  
> Use deterministic geometry code to decide exactly how to change the SVG.**

And:

> **Preserve what the local VLM already generated correctly instead of regenerating it.**

The refinement workflow exists to correct the final few structural and visual errors, not to replace the original SVG-generation model.
