# SVG Refinement — Implementation Plan

## 1. Objective

Build a minimal but extensible post-processing workflow for SVG road-sign graphics generated by the local fine-tuned VLM.

The workflow must preserve existing SVG content wherever possible.

Core rule:

> Use the multimodal foundation model to understand **what is wrong** and **which semantic geometry is involved**.  
> Use deterministic code to calculate **how the SVG must be changed numerically**.

Only arrow paths may have their internal path geometry modified.

---

## 2. Architecture

```text
Reference PNG + Input SVG
        ↓
SVG Parser / Normalizer
        ↓
Manifest + Render
        ↓
Multimodal LLM
        ↓
Structured Repair Actions
        ↓
Deterministic Repair Executor
        ↓
Updated SVG
        ↓
Render + Validation
        ↓
Repeat if necessary
```

Use one orchestrator. Do not implement a multi-agent system.

---

## 3. Implementation Phases

### Phase 1 — Minimal End-to-End Loop

Implement only:

```text
load PNG / SVG
→ parse SVG
→ assign stable IDs
→ render SVG
→ build manifest
→ Bedrock multimodal analysis
→ structured issue list
→ execute simple repair
→ re-render
```

Initial supported repairs:

- `ALIGN_COMPOSITE_CENTER`
- `REORDER_ELEMENTS`
- `REPLACE_TEXT`
- `FIT_TEXT_WIDTH`

Do not implement arrow repair until this loop works on real data.

---

### Phase 2 — Composite Geometry

Add:

- Shield grouping
- Border grouping
- Anchor selection
- Center alignment
- Basic text position correction
- Canvas-boundary correction

No non-arrow path geometry modification.

---

### Phase 3 — Arrow Geometry

After the main loop is confirmed, implement arrow-specific processing described below.

---

# 4. SVG Path Normalization for Arrows

Never depend on raw SVG path point order having semantic meaning.

The same arrow may begin at different locations and may contain extra points.

For every arrow candidate:

1. Convert all relative coordinates to absolute coordinates.
2. Expand transforms into the normalized coordinate representation where practical.
3. Parse commands into explicit segments.
4. Distinguish:
   - segment start
   - segment end
   - Bézier control points
5. Assign stable node IDs.
6. Preserve original command/segment order so edited geometry can later be serialized back.

Conceptual representation:

```text
ArrowPath
  id: path_017

  segments:
    segment_00
      type: LINE
      start: node_00
      end: node_01

    segment_01
      type: CUBIC
      start: node_01
      control_1: cp_01
      control_2: cp_02
      end: node_02
```

The LLM should reason against this normalized structure rather than the original raw `d` string.

---

# 5. Arrow Candidate Detection

Do not build a full generic arrow classifier for the demo.

Use the LLM to identify which SVG paths visually correspond to arrows by comparing:

- Reference PNG
- SVG render
- path BBox/location
- normalized path information

Expected important arrow classes:

```text
UP
UP_THEN_LEFT
UP_THEN_RIGHT
MULTI_BRANCH_GROUP
```

Occasional standalone left/right/diagonal arrows may be handled later.

---

# 6. Arrow Semantic Landmark Mapping

For each arrow, ask the LLM to map normalized nodes to semantic landmarks.

Possible landmarks:

```text
APEX

HEAD_LEFT_OUTER
HEAD_RIGHT_OUTER

LEFT_SHOULDER
RIGHT_SHOULDER

SHAFT_LEFT_BOUNDARY
SHAFT_RIGHT_BOUNDARY

LEFT_HEAD_SHAFT_JUNCTION
RIGHT_HEAD_SHAFT_JUNCTION

SHAFT_BOTTOM_LEFT
SHAFT_BOTTOM_RIGHT
```

For a horizontal head:

```text
SHAFT_UPPER_BOUNDARY
SHAFT_LOWER_BOUNDARY
```

The LLM should also return:

```text
arrow_type
head_direction
defective_side
landmark_confidence
```

Do not require all landmarks for every arrow type.

---

# 7. Landmark Validation in Code

LLM landmark output must not automatically be trusted.

Perform basic deterministic consistency checks.

Example for an upward arrow:

- left shaft boundary should normally have lower X than right shaft boundary
- shaft boundaries should be approximately parallel
- apex should be above the shaft-head junction
- shaft width must be positive
- centerline should pass approximately through the expected arrow body region

If landmark mapping is obviously inconsistent:

- do not modify the path
- request another LLM analysis or mark the arrow as unresolved

Do not create a complex validation framework; simple checks are enough.

---

# 8. Straight Up Arrow Repair Algorithm

For a straight upward arrow:

### Step A — Identify stable shaft geometry

Use the semantic landmarks to identify the left/right shaft boundaries.

Calculate:

```text
shaft_center_x =
    (shaft_left_x + shaft_right_x) / 2
```

The existing shaft width should normally be preserved.

Do not resize the shaft unless a later explicit requirement is added.

---

### Step B — Evaluate arrow head

Identify:

- apex
- left head/shoulder
- right head/shoulder
- left junction
- right junction

Check whether the arrow head is centered relative to `shaft_center_x`.

Typical malformed case:

```text
                 apex
                  ^
               __/ \__
             /         \
            /           \
           |      |      ← geometry does not reconnect correctly
           |shaft |
```

The head may be visually correct on one side but disconnected or malformed on the other.

---

### Step C — Select repair strategy

Use one of two strategies.

#### Strategy 1 — Translation of head landmarks

Use when both sides are structurally valid but the whole head is horizontally shifted.

Move the required head landmarks so the head center matches `shaft_center_x`.

Preserve local curve shape as much as possible.

---

#### Strategy 2 — Mirror the reliable side

Use when one side is correct and the opposite side is malformed.

Example:

```text
defective_side = RIGHT
```

Then:

1. keep the left-side head geometry
2. calculate its points relative to `shaft_center_x`
3. mirror those coordinates to the right
4. replace only the corresponding right-side endpoints/control points
5. reconnect to the existing right shaft boundary

Mirror around:

```text
x' = 2 * shaft_center_x - x
```

for a vertical arrow.

Do not mirror the entire arrow.

Only reconstruct the defective head/junction subgeometry.

---

# 9. Bézier Control Point Handling

When an endpoint of a Bézier segment is moved, its associated control points may also need adjustment.

Do not leave control points fixed if doing so causes the curve to deform severely.

For a translated local curve:

```text
delta = new_endpoint - old_endpoint
```

Apply the same local translation to control points belonging to that curve when appropriate.

For mirrored geometry, mirror relevant control points using the same symmetry axis.

The objective is to preserve the existing learned curve shape while restoring geometric consistency.

Do not regenerate a mathematically ideal arrow from scratch.

---

# 10. Malformed Closing Segment Detection

A common VLM failure is:

```text
correct local curve generation
→ final point does not meet expected start/junction
→ long straight segment closes the gap
```

Detect suspicious closing segments using simple geometry.

Candidate warning conditions:

- final segment is much longer than neighboring segments
- final segment crosses the expected arrow-head region
- final segment connects points that should be adjacent only after symmetry correction
- rendered result shows a missing/notched arrow side

The LLM can determine semantically whether the segment is visually incorrect.

Code should then replace the defective local geometry rather than accepting the forced closing segment.

---

# 11. Up-Then-Right Arrow

Example:

```text
      │
      │
      └────────►
```

Important rule:

> The right-facing arrow head must be aligned to the horizontal shaft centerline, not the vertical shaft centerline.

Identify:

```text
horizontal_upper_boundary
horizontal_lower_boundary
```

Calculate:

```text
head_center_y =
    (upper_y + lower_y) / 2
```

Then evaluate the right arrow head against this Y-axis centerline.

Repair using the same principles as the straight arrow:

- preserve shaft width
- preserve correct local curves
- translate the whole head if simply offset
- mirror the reliable half when one side is malformed
- repair only head/junction geometry

---

# 12. Up-Then-Left Arrow

Same as `UP_THEN_RIGHT`, using the horizontal shaft connected to the left-facing head.

Do not assume vertical and horizontal shaft widths are equal.

Each head uses the centerline of its immediately connected shaft.

---

# 13. Arrow Segment Orientation

For future extension, represent the head reference generically:

```text
head_direction = UP / LEFT / RIGHT
```

Then calculate the relevant local centerline:

```text
UP:
    center_x from left/right boundaries

LEFT or RIGHT:
    center_y from upper/lower boundaries
```

Do not build a large general geometry engine for arbitrary rotation in the first demo.

Only support actual current arrow orientations.

---

# 14. Multi-Arrow Group Detection

Several paths may belong to one arrow tree.

Example:

```text
       ↑
      /│\
     / │ \
       │
       │
```

The VLM may output three independent paths whose lower stems should overlap.

LLM responsibilities:

- identify paths belonging to the same arrow group
- identify the shared base/stem region
- identify which arrow is best aligned with the reference

Return something conceptually equivalent to:

```json
{
  "group": "arrow_group_01",
  "members": ["path_021", "path_022", "path_023"],
  "anchor": "path_021",
  "shared_region": "vertical_base"
}
```

---

# 15. Multi-Arrow Alignment Algorithm

For each group:

1. Repair internal geometry of each arrow first if necessary.
2. Identify the common stem/base landmarks.
3. Select the anchor arrow.
4. Calculate the translation required for each other arrow to align its shared stem to the anchor.
5. Translate the whole arrow path.
6. Do not change its scale.
7. Render and re-evaluate.

For a common rectangular lower stem, alignment may use:

```text
bottom-left
bottom-right
centerline
```

or the shared stem BBox center.

Do not assume the raw SVG start point is the base anchor.

---

# 16. Choosing the Arrow Anchor

Prefer an arrow whose:

- shaft width visually matches the reference
- shaft position is close to the reference
- internal geometry has high confidence
- BBox/location is already correct
- repair would require the smallest movement

The LLM may rank candidate arrows.

Code only performs the resulting relative alignment.

---

# 17. Arrow Repair Safety Rules

Arrow repair must follow these constraints:

1. Do not regenerate the whole arrow from a template.
2. Preserve existing shaft width.
3. Preserve overall position unless group alignment requires translation.
4. Preserve correct Bézier curves.
5. Modify only the minimum defective region.
6. Never change non-arrow paths during arrow repair.
7. Save the original path before modification.
8. If landmark confidence is low, leave the arrow unchanged rather than performing a large speculative edit.

---

# 18. Arrow Repair Validation

After every arrow repair:

1. Render the updated SVG.
2. Compare the repaired arrow with the Reference PNG.
3. Ask the multimodal LLM:
   - is the malformed side fixed?
   - is the head centered on the correct shaft?
   - did a new deformation appear?
   - did the arrow move away from the reference?
4. Run simple code checks:
   - SVG still parses
   - path remains closed if originally closed
   - BBox remains within a reasonable range
   - shaft width did not unexpectedly change
5. Accept or revert the repair.

For the demo, keeping one previous SVG snapshot is enough for rollback.

---

# 19. Text Repair After Arrow Geometry

Text geometry should be handled after arrow and composite-object correction.

Reason:

```text
arrow repair
→ arrow position/shape changes
→ previous text spacing may no longer be valid
```

Therefore final layout order should remain:

```text
structural geometry
→ arrow repair
→ text width / text position
→ collision correction
```

---

# 20. Main Repair Loop

Conceptually:

```text
for iteration in small_fixed_limit:

    parse current SVG
    build manifest
    render current SVG

    issues = LLM.analyze(
        reference,
        render,
        manifest,
        previous_repairs
    )

    if no important issues:
        stop

    select highest-priority safe issue

    operation = build_repair_action(issue)

    execute deterministic tool

    render again

    validate
```

Do not implement a generic planning framework around this loop.

---

# 21. Repair Priority

Recommended:

```text
1. OCR content
2. z-order
3. shield/border alignment
4. arrow internal geometry
5. arrow group alignment
6. text width
7. text position
8. collision/canvas correction
```

The orchestrator may skip unnecessary stages.

---

# 22. Implementation Rule for the Coding Agent

For the first development session:

### Implement now
- parsing
- stable IDs
- manifest
- rendering
- Bedrock call
- structured issue output
- simple center alignment
- z-order
- text replacement
- basic text fitting

### Prepare interfaces but do not fully implement yet
- path node normalization
- arrow landmark result schema
- arrow repair operation types

### Implement later after the base loop works
- Bézier-aware local path editing
- mirror repair
- turn-arrow centerline logic
- multi-arrow alignment
- arrow validation / rollback

This preserves the architecture without spending the first implementation session on the hardest geometry problem.

---

# 23. Explicit Anti-Overengineering Rules

Do not add:

- agent frameworks
- workflow engines
- provider abstraction
- generic geometry library
- generalized arrow template system
- arbitrary-angle arrow solver
- exhaustive testing
- production error handling
- database
- UI
- Docker
- CI/CD
- large configuration layer

Use direct Python code and real example data.

If a part is uncertain, leave a small TODO and continue the end-to-end workflow instead of building a generalized solution.

The architecture should eventually support:

```text
Reference
   ↓

Reliable anchors
```
